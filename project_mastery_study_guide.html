Revision & Defense Master Doc

Explainable Hybrid Deep Learning IDS for IoT Networks

Complete guide to the final, honest version of the project: what went wrong first, how we fixed it, the real results, where the code lives, and how to defend it. Every number here comes from docs/FINAL_RESULTS.md (the source of truth); if an older document disagrees, the older document is wrong.

1. Core Story & The 4 Pillars

The project in one paragraph

Goal: an IDS for IoT that is accurate (catches attacks, few false alarms), explainable (shows why it alarmed) and lightweight (fits an IoT gateway). Proposed model: a hybrid CNN-GRU with SHAP explanations. Main dataset: Edge-IIoTset (2,219,201 packets, Normal + 14 attack types). Second dataset: CICIoT2023 (flow-level, 33 attacks in 7 categories + Benign).

What we first saw, and why it was fake

Every first model (Random Forest, CNN, GRU, CNN-GRU) scored 100% on Normal vs Attack. We investigated instead of celebrating. Root cause: the dataset writes an empty protocol field as "0" in the Normal captures and as "0.0" in the attack captures. After one-hot encoding these become different columns, so one column alone gives away the label (empty dns.qry.name.len: "0" = 1,613,798 Normal rows and 0 attacks; "0.0" = 0 Normal rows and 603,331 attacks). The same happens in mqtt.topic, mqtt.protoname, mqtt.conack.flags. Our earlier "fix" of removing MQTT did not help, because the DNS column carries the same artifact, and our SHAP plots had hidden it by stripping the _0 / _0.0 suffix from feature names.

Honest pipeline flow (final)

Raw Edge-IIoTset ➔ Canonicalise ("0" = "0.0") ➔ Strict feature policy (drop 7 per-packet identifiers + all mqtt.*; 51 encoded features) ➔ Shortcut scans (single-feature stumps, depth-3 tree) ➔ GPU training, 3 seeds, threshold chosen on validation only ➔ Tuned CNN-GRU (Macro-F1 0.858, 79,169 params) ➔ Detection ceiling audit ➔ SHAP + fidelity test ➔ Edge benchmark (FP16, 159 KB) ➔ Repeat on CICIoT2023.

Pillar 1: Honest Accuracy

After removing the shortcut, the tuned CNN-GRU scores Macro-F1 0.858 (90.0% accuracy, 0.7% false alarms, 65.3% of attacks detected). A measured ceiling shows even a perfect memoriser detects only 67.5%, so the model is at the limit of what these packet features allow.

Pillar 2: Proven Explainability

SHAP top features are real TCP behaviour (tcp.flags, tcp.connection.rst, tcp.flags.ack, tcp.len, tcp.connection.fin). Retraining without the top-5 SHAP features drops Macro-F1 0.858 → 0.605; without 5 random features it stays 0.858. SHAP is faithful.

Pillar 3: Edge Feasibility

Final CNN-GRU is 315 KB; the FP16 version is 159 KB with no loss (0.858). On 1 CPU thread: about 6.5 ms per packet. INT8 on the GRU shrinks it to 88 KB but costs 7.6 points.

Pillar 4: Second Dataset

On CICIoT2023 (flow-level, has rate and timing) we found and removed a second hidden shortcut (window size). Honest binary Macro-F1: CNN-GRU 0.890, XGBoost 0.917; 8 categories: 0.675 / 0.752.

2. Code Walkthrough: What to Open & Show

If faculty asks to see the code, follow the story: evidence of the shortcut ➔ the fix ➔ training ➔ explanations ➔ experiments ➔ results.

audit_shortcuts.py

Shortcut evidence: --raw streams the CSV and counts how each class writes empty fields (results/audit/empty_token_audit.csv). Also fits one-feature stumps and a depth-3 tree on processed data to catch any remaining giveaway.

💬 Say: "This is the proof that the 100% was fake: one column, written as "0" vs "0.0", separates Normal from Attack."
src/preprocessing.py

The fix: canonicalize_column() merges "0" and "0.0" before encoding; feature_fingerprint() writes a fingerprint of the processed data into metadata.json. Streaming, low-RAM (peak 6.1 → 3.4 GB).

💬 Say: "We canonicalise numeric text, apply the strict feature policy, and stamp the data with a fingerprint so no model can be trained or explained on the wrong data."
src/training.py

Training engine: data held on the GPU (≈8 s/epoch vs ≈31 s), Adam, early stopping on validation loss, optional sqrt class weights, and choose_threshold() which picks the decision threshold on validation only.

💬 Say: "The test set is never used for any choice. The threshold comes from validation, and every comparison is run with 3 seeds."
src/models.py

Architectures: MLP, CNN1D, GRUBaseline and the proposed CNN_GRU (Conv1D ➔ BatchNorm ➔ ReLU ➔ MaxPool ➔ Dropout ➔ GRU ➔ Dense ➔ output).

💬 Say: "The convolution learns local feature combinations, the GRU reads the resulting feature map step by step. The same file holds the simpler baselines we compared against."
src/explainability.py

SHAP engine: shap.GradientExplainer. _check_data_matches_experiment() refuses to run if the data fingerprint differs from the one the model was trained on.

💬 Say: "An earlier SHAP plot explained a model with the wrong inputs. This guard makes that impossible now."
run_clean_baselines.py

Clean baselines: XGBoost (GPU) and CNN-GRU on the canonicalised data, per feature policy (e.g. --policy strict_no_mqtt --stage binary).

💬 Say: "These are the honest numbers after the fix, for both a tree model and our network."
run_tune_cnn_gru.py

Tuning: Optuna, 20 trials, then retrains the best setting with 3 seeds (F_strict_no_mqtt_binary_best_s42/s7/s2024).

💬 Say: "Best validation 0.8596, test 0.858, the same as untuned. Tuning cannot beat the ceiling."
run_final_studies.py

Final studies: ablation (MLP / 1D-CNN / GRU, 3 seeds), SHAP on the final model, SHAP fidelity (drop top-5 vs 5 random features), edge benchmark.

💬 Say: "This is where we test our own claims: is the hybrid needed, and is SHAP faithful?"
run_edge_benchmark.py

Edge test, CPU only: FP32, FP16, INT8 versions and XGBoost; Macro-F1, file size, single-packet latency on 1 thread, throughput ➔ results/edge_benchmark.csv.

💬 Say: "A gateway has no GPU, so we measured on one CPU thread."
audit_ceiling.py

Detection ceiling: groups identical feature vectors; if a pattern is mostly Normal, any classifier must call it Normal ➔ results/audit/detection_ceiling.json.

💬 Say: "Only 11,122 distinct patterns in 1.55 million training packets; even a perfect memoriser detects 67.5% of attacks."
run_ciciot.py + src/ciciot.py

Second dataset: same honest pipeline on CICIoT2023 (--policy strict): duplicates removed before splitting, source_file, packet_count and total_sum dropped, flag counts turned into fractions.

💬 Say: "We found a second shortcut here: the window size reveals the label. We removed it too."
watch_dashboard.py

Live terminal dashboard: reads the status/progress files and the registry while a run is going; can be opened or closed without affecting the run.

💬 Say: "Long runs are monitored live: epoch, loss, early-stopping counter, finished experiments."
make_figures.py

Figures: builds results/figures/fig1..fig5 from the committed result files.

💬 Say: "Every chart is generated from result files, not drawn by hand."

3. Deep Dive: What is `best_model.pt`?

What does it represent?

best_model.pt is the PyTorch file holding the trained weights (the state_dict). The training loop saves it every time validation loss improves, so it is the best epoch on validation. The final one is results/experiments/F_strict_no_mqtt_binary_best_s42/best_model.pt: the tuned CNN-GRU with 79,169 parameters, 315 KB on disk (FP16 copy: 159 KB). It is the file the SHAP script and the edge benchmark load.

Do not show the old checkpoints as final

Older folders such as E01–E08 were trained on the leaky data (before the "0"/"0.0" fix). Their "100%" results and their sizes belong to the "what we first saw" story only.

4. IoT Real-World Deployment Architecture

Sensors (smart meters, bulbs, temperature probes) do not run the AI. The model is meant to run on the IoT edge gateway (e.g. a Raspberry-Pi-class device). We benchmarked on a laptop CPU with 1 thread; testing on a real Pi is a next step.

The 5-Step Execution Lifecycle

1. Packet Ingestion: Device traffic passes through the gateway.
2. Feature Extraction: Gateway extracts the same 51 encoded features used in training (same canonicalisation and feature policy).
3. AI Inference: FP16 CNN-GRU (159 KB) scores the packet, about 6.5 ms per packet on 1 CPU thread.
4. Decision: Score above the validation-tuned threshold ➔ Attack alert; otherwise Normal. The threshold can be moved to trade detections against false alarms.
5. Explainable Alert: SHAP shows which features pushed the score (e.g. unusual tcp.flags / tcp.connection.rst). A live demo through the dashboard predict API is a next step.

C. Input features (Edge-IIoTset final setting: strict_no_mqtt, 51 encoded features)

Kept

TCP: tcp.flags, tcp.flags.ack, tcp.len, tcp.connection.syn/synack/fin/rst. HTTP: method, version, referer, content length, response. DNS: query name/length/type, retransmissions. Plus ARP, ICMP and Modbus length fields.

Removed

Starting from the operational policy (already no IPs, ports or timestamps): minus 7 per-packet identifiers (tcp.seq, tcp.ack, tcp.ack_raw, tcp.checksum, icmp.checksum, icmp.seq_le, udp.stream) and minus every mqtt.* field (every MQTT packet in the dataset is Normal).

CICIoT2023 uses flow-level features (e.g. header_length, rate, flag fractions, protocol indicators) with source_file, packet_count and total_sum removed.

7. 5-Minute Faculty Presentation Script

Stage 1: Problem Statement (40 sec)

"Good morning sir/ma'am. Our project is Explainable Hybrid Deep Learning-Based Intrusion Detection for IoT Networks. IoT devices are easy to attack and too weak to run heavy security software. We want an IDS that is accurate, explainable, and light enough for an IoT gateway. Our model is a hybrid CNN-GRU with SHAP explanations, tested on Edge-IIoTset and CICIoT2023."

Stage 2: The 100% Was Fake (60 sec)

"Our first models all scored 100%. Instead of celebrating, we investigated. The dataset writes an empty field as "0" in normal traffic and "0.0" in attack traffic, so after encoding a single column gives away the label. We fixed it by treating "0" and "0.0" as the same value, removed 7 per-packet identifiers and all MQTT fields, and added automatic shortcut scans and data-fingerprint guards. Figure 1 shows the fake 100% next to the honest result."

Stage 3: Honest Results & the Ceiling (70 sec)

"On the clean data, our tuned CNN-GRU reaches Macro-F1 0.858: 90% accuracy, 0.7% false alarms, and it detects 65.3% of attacks. It is stable across 3 seeds, and tuning with 20 Optuna trials does not raise it. We measured why: the 1.55 million training packets have only 11,122 distinct feature patterns, and a third of attack packets look exactly like normal ones. Even a perfect memoriser detects only 67.5%, so our model is at the ceiling of what single packets allow."

Stage 4: Explainability That Is Proven (50 sec)

"SHAP says the model relies on real TCP behaviour: tcp.flags, connection resets, ACK flags, packet length. We did not just trust the plot. We retrained without SHAP's top-5 features and Macro-F1 fell from 0.858 to 0.605; removing 5 random features changed nothing. So the explanation is faithful."

Stage 5: Edge & Second Dataset (50 sec)

"The final model has 79,169 parameters; in FP16 it is 159 KB with no loss, at about 6.5 ms per packet on one CPU thread. On CICIoT2023, which has flow-level rate and timing, we found and removed a second hidden shortcut, and the CNN-GRU reaches 0.890 binary and 0.675 on 8 attack categories, up from 0.34 on packet data."

Stage 6: Honest Limits & Next Steps (40 sec)

"To be transparent: on per-packet features the CNN-GRU is not better than an MLP or XGBoost, because the GRU sees no real time dimension. Next we will give the GRU real sequences of flow windows, run a cross-dataset test, and deploy the FP16 model on a Raspberry-Pi-class device. Our contribution: two hidden dataset shortcuts found and removed, a measured ceiling, proven SHAP fidelity, and a fully reproducible evaluation. Thank you."

8. Tough Faculty Defense Q&A

Q1: Your first models got 100%. Why is the final result lower?
"The 100% was fake. Empty fields were written as "0" in normal captures and "0.0" in attack captures, so one column revealed the label. Every model, including Random Forest, exploited it. After the fix the honest result is 0.858 Macro-F1. A lower honest number is worth more than a perfect fake one."
Q2: Isn't 65% detection too low for an IDS?
"It is low, and we measured why: 31.9% of attack packets have exactly the same features as mostly-normal patterns, so no packet-level model can catch them. The ceiling is 67.5%; we reach 65.3% (XGBoost 67.3%). The threshold can be lowered to reach 73.3% at 6.6% false alarms. With flow-level data (CICIoT2023) detection rises to 90.4%."
Q3: If an MLP gets the same 0.858, why the hybrid CNN-GRU?
"Honest answer: on per-packet features the hybrid gives no accuracy gain; MLP, 1D-CNN, GRU and CNN-GRU all score 0.858 because they all hit the ceiling. The GRU needs a real time dimension to help. Our next step is to feed it consecutive flow windows per device or connection, which is where a recurrent model should pay off."
Q4: XGBoost is slightly better and much faster. Why not just use it?
"XGBoost is a strong baseline and we report it openly: 0.868 vs 0.858, 0.8 ms vs 6.5 ms per packet. The networks are smaller (FP16 CNN-GRU 159 KB, MLP 24 KB, XGBoost 492 KB). If CPU speed on per-packet data were the only goal, XGBoost would be a fair choice; the CNN-GRU is kept because the next step feeds it real sequences of flow windows, where a recurrent model can use time and a tree model cannot."
Q5: How do you know SHAP is telling the truth?
"We tested it. Retraining without SHAP's top-5 features drops Macro-F1 from 0.858 to 0.605; retraining without 5 random features changes it by only 0.0001. We also added a guard so SHAP refuses to run on data the model was not trained on, because an earlier plot had explained a model with the wrong inputs."
Q6: Earlier you said MQTT fields drive detection. What changed?
"That came from the leaky data: the MQTT fields carried the same "0"/"0.0" artifact, and every MQTT packet in the dataset is Normal. We now remove all MQTT fields; with vs without MQTT gives 0.8579 vs 0.8575, so the model does not use them. The real top features are TCP flags, resets, ACKs and packet length."
Q7: Why is attack-type (multiclass) detection so weak?
"On Edge-IIoTset strict features, Macro-F1 is 0.337 for CNN-GRU and 0.429 for XGBoost. Floods and scans are defined by packet rate, which a single packet cannot show, and the dataset has no timing for attack packets (udp.time_delta is 0 for every attack row). On CICIoT2023, which has rate, it rises to 0.675 (CNN-GRU) and 0.752 (XGBoost)."
Q8: Did you try focal loss or class weights for imbalance?
"Yes, over 3 seeds on multiclass: sqrt class weights 0.337 beat focal loss 0.254 and cross-entropy 0.238. Sqrt weights also help on CICIoT2023 categories (0.675 vs 0.620). For the binary model, plain cross-entropy was kept."
Q9: How can we trust there is no other leakage?
"Automatic shortcut scans fit a one-feature stump per column and a depth-3 tree; a giveaway shows up as near-100%. On CICIoT2023 the best single feature reaches only 0.85 after the fix. Thresholds are chosen on validation only, every comparison uses 3 seeds, and a data fingerprint stops training or SHAP on mismatched data. Limitation: one random stratified split per dataset and no cross-dataset test yet."
Q10: Where does this model sit in an IoT network, and is it fast enough?
"On the IoT edge gateway, not on sensors. On one CPU thread the FP16 model is 159 KB and takes about 6.5 ms per packet (around 1,660 packets/s). It raises explainable alerts; we have not yet tested it on a real Raspberry Pi, which is a next step."
Q11: How does SHAP work in simple terms?
"SHAP comes from Shapley values in game theory. Each input feature is a 'player', and SHAP measures how much each one pushed this packet's score toward Attack or Normal, compared with an average background. We use the gradient-based version for neural networks."
